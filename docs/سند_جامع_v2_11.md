## دستاوردهای ساختاری

- **چهار قانون UX جدید (#۶۲-۶۵)** که سبک تعامل Claude-کاربر را به نقطه پایدارتری می‌رساند
- **یک درس جدید (M63)** درباره مدیریت status صریح در handoff
- **حل ریشه‌ای ابهام handoff** — هر گام آینده با prefix صریح (✅ DONE / 📋 TODO / ⚠️ CHECK / 💡 NOTE) همراه است

## قوانین رفتاری جدید Claude (#۶۲ تا #۶۵)

- **#۶۲** ⭐: **فایل handoff دائمی** — در پایان هر چت، فایل `claude_workspace/incoming_permanent/CHAT{N+1}_HANDOFF.txt` ساخته شود. متن inline تنها کافی نیست (M58). هر آیتم باید با یکی از prefix های `✅ DONE`، `📋 TODO`، `⚠️ CHECK`، `💡 NOTE` همراه باشد (افزوده در v2.11 بر اساس M63).
- **#۶۳** ⭐: **Convention `🟢 ▶️ EXECUTE`** — هر گام اجرایی که نیاز به copy-paste/اجرای فرمان توسط کاربر دارد، با تیتر سبز `## 🟢 ▶️ EXECUTE — اقدام لازم` شروع می‌شود + شامل نام tab + رنگ tab مطابق قانون #۳۱. هدف: تشخیص بصری سریع تفاوت بین «توضیح» و «اقدام لازم».
- **#۶۴** ⭐: **عدم نمایش جزئیات تصحیح خطای کد** — وقتی کد به خطا می‌خورد، Claude (الف) علت را در ذهن خود بررسی می‌کند (ب) **توضیحات «چرا خطا داد» و «چطور تشخیص دادم» را به کاربر نشان نمی‌دهد** (ج) فقط گام اجرایی کد اصلاحی را با Convention #۶۳ ارائه می‌دهد. استثنا: گزارش کارها، درس M-numbered، توضیح معماری.
- **#۶۵** ⭐: **ثبت درس از اشتباهات با نمایش** — درس کلی (M-numbered) به کاربر **نمایش داده می‌شود** (نه پنهان). تفاوت با #۶۴: درس **چه** آموختیم → نمایش، **چرا** خطا داد و **چطور** تشخیص → پنهان.

## درس‌نامه جدید (M63)

- **M63:** **فرض نکردن وضعیت کارهای infrastructure در handoff** — اگر در handoff موردی ذکر شده ولی status صریح ندارد، Claude باید بپرسد، نه فرض کند. خصوصاً برای کارهای خارج فایل‌سیستم پروژه (Project در Claude Desktop، GitHub settings، Connectors، ...). کشف شد در ابتدای چت ۹.

## فلسفه این نسخه — تثبیت سبک تعامل

## ۶.۱  Auth Flow

| مرحله | عملیات | توضیح |
|---|---|---|
| ۱ | `POST /api/v1/auth/login` | دریافت username و password |

| ۷ | خروج | `POST /auth/logout` — ابطال Refresh در DB |

## ۶.۱۱  🆕 v2.1 — WebSocket Authentication ⭐

احراز هویت WebSocket با handshake JSON پس از اتصال (به‌جای query parameter).

روش انتخاب‌شده: پس از باز شدن اتصال WebSocket، client باید به‌عنوان اولین پیام، یک JSON با ساختار زیر ارسال کند:

```json
{
  "type": "auth",
  "token": "<JWT access token>"
}
```

Server این پیام را بررسی می‌کند:

- اگر token معتبر بود → پاسخ `{"type": "auth", "status": "ok"}` ارسال و اتصال ادامه پیدا می‌کند
- اگر token نامعتبر بود یا طی ۵ ثانیه auth نیامد → server اتصال را با کد 1008 می‌بندد

**دلیل انتخاب این روش (به‌جای query string):** token در URL ثبت نمی‌شود (لاگ Nginx، تاریخچه مرورگر، Referer header).

🔒 Claude باید Reconnection خودکار با Exponential Backoff در هر دو طرف پیاده‌سازی کند.

🔒 هیچ Endpoint ای بدون Validation ورودی با Pydantic ایجاد نشود.

```jsx
<div style={{
  background: cfg.color,                  // ❌ هویت تم نابود
```

# سند ۹ — استانداردهای امنیت

## ۹.۱  احراز هویت

🔒 رمز عبور با bcrypt hash ذخیره شود — هرگز Plain Text.

🔒 Session Timeout: ۳۰ دقیقه — Access Token: ۳۰ دقیقه — Refresh Token: ۷ روز.

- JWT Secret از `.env` — هرگز Hardcode
- در صورت ورود مشکوک، تمام Refresh Tokenهای کاربر ابطال شوند

🆕 **v2.5 — پیاده‌سازی واقعی:**

- **bcrypt مستقیم (نه passlib):** پس از ناسازگاری `passlib 1.7.4` با `bcrypt 4.x` (تصمیم #40)، در `app/core/security.py` مستقیم از کتابخانه `bcrypt` استفاده می‌شود. تابع `hash_password()` و `verify_password()` با رعایت محدودیت ۷۲ بایت bcrypt پیاده‌سازی شده‌اند.
- **Refresh Token در DB (`Sessions` table):** هر login یک رکورد جدید با `token`, `expires_at`, `is_revoked` می‌سازد. logout صرفاً `is_revoked=True` می‌کند (نه حذف فیزیکی).
- **JWT در localStorage (فاز ۰):** برخلاف توصیه نهایی (HttpOnly Cookie) که در فاز ۵+ پیاده می‌شود، در فاز ۰ از `localStorage` با Zustand `persist` استفاده می‌شود. علت: ساده‌تر برای dev، CSRF در فاز ۰ مسئله نیست (single-user local). **مهاجرت به HttpOnly Cookie در فاز ۵ (security hardening) قطعی است.**
- **OAuth2PasswordRequestForm:** endpoint `/auth/login` با `application/x-www-form-urlencoded` کار می‌کند (نه JSON) — استاندارد OAuth2. Swagger UI خودش UI Authorize می‌سازد.

## ۹.۲  رمزنگاری API Key صرافی

🆕 v2.1 — روش رمزنگاری از AES-256 خام به `cryptography.Fernet` تغییر کرد.

🔒 API Key و Secret Key صرافی‌ها باید با `cryptography.Fernet` رمزنگاری شوند.

Fernet در باطن از AES-128-CBC + HMAC-SHA256 استفاده می‌کند و یک استاندارد امن و ساده است که خطای پیاده‌سازی نمی‌دهد.

- **کلید Fernet (44 کاراکتر):** از متغیر محیطی `ENCRYPTION_KEY` در `.env` خوانده می‌شود
- **تولید کلید:** در اولین اجرای setup به‌صورت تصادفی توسط `cryptography.fernet.Fernet.generate_key()` تولید می‌شود
- **هشدار حیاتی:** اگر فایل `.env` گم شود، تمام API Keyهای رمزنگاری‌شده غیرقابل بازیابی خواهند بود — صاحب پروژه باید بک‌آپ امن داشته باشد
- امکان محدود کردن: read-only یا read+trade
- در Log هرگز API Key نمایش داده نشود (فیلتر خودکار در `logging.py`)

## ۹.۳  کنترل دسترسی (RBAC)

- نقش‌ها: Admin، Trader، Viewer، API User
- 🆕 v2.1 — Audit Log در جدول `AuditLog` (سند ۵ بند ۵.۱۲): ثبت تمام عملیات مهم با `user_id, IP, user_agent, timestamp, details JSON`
- Row-Level Security: کاربر فقط داده‌های خودش را ببیند

## ۹.۴  محافظت از حملات

| حمله | روش محافظت |
|---|---|
| **SQL Injection** | SQLAlchemy ORM — هرگز Query خام با ورودی کاربر |
| **XSS** | Input Sanitization — Content Security Policy Header |
| **CSRF** | CSRF Token در فرم‌های مهم |
| **Brute Force** | Rate Limiting روی `/auth/login` — حداکثر ۵ تلاش |
| **Path Traversal** | اعتبارسنجی مسیر فایل‌ها |
| **WebSocket Token Leak** | 🆕 v2.1 — handshake JSON پس از اتصال (نه query string) |

## ۱۳.۶  🆕 v2.6 — قالب نام چت (Chat Naming Convention) ⭐

> ⚠️ **اصلاحیه v2.7:** فرمت اصلی `phase{NN}` به `phase{N}` تک‌رقم 0-based تغییر یافت (بر اساس درخواست کاربر در ابتدای Session 6).

### ۱۳.۶.۱  فرمت اجباری (به‌روز v2.7)

```
TRADING-phase{N}-part{NN}-{topic-slug}
```

- `{N}`: تک‌رقم — `phase0`, `phase1`, `phase2`, … (همان شماره فاز سند ۱۲، 0-based)
- `{NN}`: دو رقم — `part01`, `part02`, …
- `{topic-slug}`: kebab-case، بر اساس **موضوعات واقعی** انجام‌شده در چت

### ۱۳.۶.۲  مثال‌های واقعی (به‌روز v2.7)

| چت | نام |
|---|---|
| اولین چت پروژه | `TRADING-phase0-part01-setup` |
| Theme Engine | `TRADING-phase0-part04-theme-engine` |
| Skeleton + ConfirmDialog → گسترش | `TRADING-phase0-part05-ui-polish-and-governance` |
| CCXT + WebSocket | `TRADING-phase1-part01-ccxt-websocket-setup` |
| Indicators پایه | `TRADING-phase2-part01-indicators-foundation` |

> ⚠️ **مثال‌های قدیمی منسوخ** (در v2.6): `phase01-part01-...` ❌ → `phase0-part01-...` ✅

### ۱۳.۶.۳  قوانین انتخاب topic-slug

- ۲ تا ۴ کلمه
- kebab-case (با خط تیره)
- توصیفی نه عمومی
- بر اساس **موضوعات واقعی** انجام‌شده، نه برنامه اولیه

# سند ۲۰ — Pre-commit Hooks Philosophy ⭐ 🆕 v2.9

> **هدف:** توجیه طراحی Hybrid mode و trade-offs آن.

## ۲۰.۱  ۳ گزینه ممکن

| حالت | اجباری/Warning | مزیت | عیب |
|---|---|---|---|
| **همه اجباری** | همه fail commit | کد بد وارد نمی‌شود | WIP موقت سخت، اگر hook bug، قفل |
| **همه warning** | فقط چاپ هشدار | workflow هرگز قفل نمی‌شود | معمولاً نادیده گرفته می‌شود |
| **Hybrid** ⭐ | critical اجباری، minor warning | تعادل | پیچیدگی config |

## ۲۰.۲  انتخاب پروژه: Hybrid

| Hook | حالت | چرا |
|---|---|---|
| `trailing-whitespace`, `end-of-file-fixer`, `check-yaml`, `check-json` | 🔴 اجباری (auto-fix) | استاندارد عمومی |
| `black`, `isort` | 🔴 اجباری (auto-fix) | یکنواختی مطلق Python |
| `check-anti-patterns` -- A1 (hex), A4 (secret), A8 (localStorage), A10 (sync I/O) | 🔴 اجباری | security/bug-prone |
| `check-anti-patterns` -- A6 (print) | 🟡 warning | dev موقت |
| `pytest-unit`, `vitest` | حذف از pre-commit | کند، انتقال به pre-push (آینده) |

## ۲۰.۳  Bypass در اضطرار (قانون #۴۲)

```cmd
git commit --no-verify -m "[skip-hooks: REASON] ..."
```

### موارد قابل قبول
- Hook خود bug دارد
- Migration حساس
- WIP موقت قبل از merge

### موارد غیرقابل قبول
- «hook کنده، صبر ندارم»
- «A1 violation است ولی موقتی»

## ۲۰.۴  Mass Reformat در شروع

اولین اجرای hooks در پروژه legacy، انبوه فایل را reformat می‌کند (در چت ۷، ۷۸ فایل + ۶۰ فایل CRLF). این طبیعی است:

```cmd
pre-commit run --all-files
git add -A
git commit --no-verify -m "style: apply black/isort to legacy files [skip-hooks: mass-format]"
```

# سند ۲۱ — اتصال به GitHub در شروع پروژه ⭐ 🆕 v2.9

> **هدف:** چک‌لیست استاندارد اتصال پروژه به GitHub که در شروع هر پروژه باید انجام شود.
> **نکته:** این کار در شروع این پروژه فراموش شد. در چت ۸ جبران می‌شود.

## ۲۱.۱  چرا اول پروژه؟

- Backup remote (در صورت crash hard disk)
- Time-machine کامل کد
- آمادگی برای CI/CD آینده
- آمادگی برای collaboration

## ۲۱.۲  چک‌لیست استاندارد

### مرحله ۱ -- ایجاد repository در GitHub

🟧 **tab «3 frontend»** (مرورگر)

1. ورود به github.com
2. کلیک `New repository`
3. نام: `trading-system`
4. **Private** (پیشنهاد - تا فاز ۴)
5. **بدون** README/license/.gitignore (چون از قبل داریم)
6. کلیک `Create repository`

### مرحله ۲ -- تأیید `.gitignore` شامل secrets

🟥 **tab «4 BACKUP»**

```cmd
findstr "\.env" .gitignore
:: باید `.env` و `.env.local` و مشابه چاپ شوند
```

### مرحله ۳ -- اتصال local به remote

🟥 **tab «4 BACKUP»**

```cmd
cd D:\Projects\trading-system
git remote add origin https://github.com/<USERNAME>/trading-system.git
git branch -M main
git push -u origin main
```

اولین push کند است (همه history).

### مرحله ۴ -- تنظیم authentication

#### گزینه ۱ -- Personal Access Token (ساده‌تر)

1. GitHub Settings → Developer settings → Personal access tokens → Tokens (classic)
2. Generate new token (Classic)
3. Scope: `repo`
4. Token را کپی کنید
5. اولین `git push` username + token می‌خواهد

#### گزینه ۲ -- SSH key (امن‌تر، توصیه برای استفاده مکرر)

```cmd
ssh-keygen -t ed25519 -C "your_email@example.com"
type %USERPROFILE%\.ssh\id_ed25519.pub
```

سپس public key را در GitHub Settings → SSH and GPG keys اضافه کنید.

### مرحله ۵ -- تأیید push موفق

```cmd
git status
git log --oneline -5
```

## ۲۱.۳  Best Practices

- **هرگز** `.env` را commit نکنید
- **هرگز** API keys را در commit بگذارید
- از **branch protection** برای `main` در GitHub Settings استفاده کنید (آینده)
- **regular push** -- هر چند commit یک‌بار push کنید

# سند ۲۲ — Filesystem MCP Integration ⭐ 🆕 v2.10

> **هدف:** راهنمای استفاده عملی از Filesystem MCP که در چت ۷ نصب شد و در چت ۸ به‌طور گسترده استفاده می‌شود. این بخش مکمل قوانین #۴۹، #۵۱، #۶۰ است.

## ۲۲.۱  چیست و چرا؟

Filesystem MCP (Model Context Protocol) یک extension برای Claude Desktop است که به Claude اجازه می‌دهد مستقیماً با فایل‌سیستم کاربر تعامل کند — خواندن، نوشتن، edit، list، جستجو. این جایگزین workflow قدیمی است که در آن کاربر باید paste طولانی محتوای فایل می‌داد.

**مزایا:**
- متن handoff شروع چت **کوتاه** می‌شود (قانون #۵۰)
- Claude می‌تواند فایل‌ها را **مستقیم** بخواند و ویرایش کند
- اصلاحات کوچک با `edit_file` بدون اسکریپت Python ممکن است
- read-back verify (قانون #۳۷) سریع و خودکار
- ثبت لحظه‌ای PENDING-EOC (قانون #۶۰) ممکن می‌شود

## ۲۲.۲  Tools موجود

| دسته | Tool | کاربرد | نیاز به تأیید |
|---|---|---|---|
| **read** | `list_allowed_directories` | لیست پوشه‌های قابل دسترس | ❌ |
| **read** | `list_directory` | لیست فایل/پوشه | ❌ |
| **read** | `list_directory_with_sizes` | لیست + اندازه | ❌ |
| **read** | `directory_tree` | ساختار درختی JSON | ❌ |
| **read** | `read_text_file` | خواندن فایل (با head/tail/view_range) | ❌ |
| **read** | `read_multiple_files` | چند فایل همزمان | ❌ |
| **read** | `get_file_info` | متادیتا | ❌ |
| **read** | `search_files` | جستجوی glob | ❌ |
| **write** | `write_file` | ساخت/overwrite | ✅ تأیید |
| **write** | `edit_file` | edit با git-style diff | ✅ تأیید |
| **write** | `create_directory` | ساخت پوشه | ✅ تأیید |
| **write** | `move_file` | move/rename | ✅ تأیید |
| **write** | `copy_file_user_to_claude` | کپی به Claude sandbox | ✅ تأیید |

## ۲۲.۳  Permissions Setup (قانون #۴۹)

در Claude Desktop → Settings → Connectors → Filesystem MCP:

- **Always Allow:** همه read-only tools
- **Needs Approval:** همه write/delete/copy tools
- **پوشه مجاز:** فقط `D:\Projects\trading-system` (و subdirectoryها)
- **محدودیت‌ها:**
  - هرگز `.env` تغییر داده نشود
  - هرگز خارج پوشه پروژه عمل نشود
  - هرگز فایل سیستمی (Windows) خوانده نشود

## ۲۲.۴  Workflow عملی

چرخه استاندارد یک عمل write:

```
1. Preview ساختار قبل از write   (M60)
2. درخواست تأیید از کاربر         (قانون #۵۱)
3. اجرای write_file یا edit_file
4. read-back verify فایل           (قانون #۳۷، M61)
5. گزارش به کاربر                  (قانون #۵۹: مسیر صریح)
```

**مثال:** edit در سند جامع:

1. `read_text_file` با `view_range` برای دیدن متن دقیق
2. آماده‌سازی `edits` array با old_str/new_str دقیق
3. اعلام به کاربر: «این edit را اعمال می‌کنم»
4. اجرای `edit_file` با دریافت تأیید
5. `read_text_file` با `view_range` روی همان محل برای verify
6. گزارش موفقیت

## ۲۲.۵  استثنائات و توصیه‌ها

- **MCP در چت جاری load نمی‌شود (M30):** اگر در همین چت Filesystem MCP فعال شد، در همین چت کار نمی‌کند. باید چت جدید باز شود.
- **مسیر تحویل صریح (قانون #۵۹):** بعد از هر write، Claude باید مسیر فایل را اعلام کند: `D:\Projects\trading-system\path\to\file.md`
- **`.env` ممنوع:** حتی اگر کاربر بخواهد، `.env` نباید با MCP تغییر داده شود. به‌جای آن، اسکریپت Python idempotent ارائه شود.
- **حجم فایل:** فایل‌های بزرگ‌تر از ~۲۰۰KB با MCP کند هستند. برای فایل‌های بزرگ، اسکریپت Python بهتر است.

## ۲۲.۶  Troubleshooting

| مشکل | علت | راه‌حل |
|---|---|---|
| `Path not allowed` | پوشه در permissions نیست | بررسی `list_allowed_directories` |
| `Empty edits array applied diff` | bug احتمالی MCP server | با `read_text_file` verify کن — بسیاری اوقات edit واقعاً اعمال شده |
| `edit_file` با match نشدن `oldText` | encoding/whitespace/زبان فارسی | اول `read_text_file` با `view_range` کن، سپس exact copy |
| فایل‌های فارسی نام | شناسایی مسیر | همیشه با `\` و نام exact (بدون normalize) |

# سند ۲۴ — claude_workspace Structure 🆕 v2.10

> **هدف:** ساختار استاندارد پوشه `claude_workspace/` که در چت ۷ ساخته شد و قوانین #۵۶-۵۹ به آن مربوط می‌شوند.

## ۲۴.۱  ساختار ۵-پوشه

```
D:\Projects\trading-system\claude_workspace\
├── incoming_permanent\    ← فایل‌های دریافتی دائم از کاربر
│   └── .gitkeep
├── old_versions\          ← نسخه‌های قدیمی فایل‌ها
│   └── .gitkeep
├── screenshots\           ← screenshots آپلودی کاربر (قانون #۵۷)
│   └── .gitkeep
├── snapshots\             ← snapshot های Project Knowledge (قانون #۵۸)
│   └── .gitkeep
└── zip_temp\              ← zip های موقت
    └── .gitkeep
```

## ۲۴.۲  وظیفه هر پوشه

| پوشه | کاربرد | گیت |
|---|---|---|
| `incoming_permanent/` | فایل‌هایی که کاربر یک‌بار آپلود می‌کند و در پروژه می‌ماند (مثل فایل Excel ورودی، logo، asset) | tracked |
| `old_versions/` | نسخه‌های قدیمی فایل‌ها قبل از حذف کامل (تاریخ‌بندی شده) | tracked |
| `screenshots/` | screenshots آپلودی کاربر برای دیباگ، توضیح، یا audit (قانون #۵۷) | **gitignored** |
| `snapshots/` | snapshot های Project Knowledge با timestamp (قانون #۵۸) | tracked برای تاریخچه |
| `zip_temp/` | zip های موقت (extract شده یا در حال ساخت) | **gitignored** |

## ۲۴.۳  Policy `.gitignore`

```gitignore
# claude_workspace policy
claude_workspace/screenshots/*
!claude_workspace/screenshots/.gitkeep
claude_workspace/zip_temp/*
!claude_workspace/zip_temp/.gitkeep
```

## ۲۴.۴  ارتباط با قوانین

- **قانون #۵۶:** هر فایل تولیدی Claude → مسیر صریح در `claude_workspace/` یا `docs/` یا `scripts/`

- `pdf` — PDF
- `frontend-design` — React/Vue UI
- `file-reading` — مسیریابی فایل
- `skill-creator` — meta — ساخت skill جدید

## ۲۵.۵  ساختار Skill

هر skill یک پوشه با حداقل این فایل‌ها:

```
skills/trading-{name}/
├── SKILL.md          ← دستورالعمل اصلی
├── examples/         ← مثال‌های use case
│   └── example1.md
└── templates/        ← قالب‌های reusable
    └── template.py
```

## ۲۵.۶  پروتکل ساخت Skill جدید

1. تشخیص task تکراری توسط Claude

4. ثبت در این بخش (به‌روزرسانی جدول ۲۵.۲)
5. اعمال در چت‌های بعد
